# Evidence analysis providers

`server.analysis_engine.analyze_evidence(records, vehicle, market, provider)` is a pure analysis boundary. It returns source-linked findings and requirement proposals; the workflow layer owns persistence, stable requirement identities, scoring, decisions and revision history. Input evidence must have unique internal IDs: the original BMW spreadsheet's `ID` is not unique across rows.

Vehicle/market scope identifies the predecessor evidence, starting with G60/US. Requirements target the successor to that vehicle with an assumed 3–5-year introduction horizon. Proposals state the horizon and extrapolation to future customers as PM planning assumptions, while source labels retain the current vehicle and market.

## Deterministic reference mode

The default `deterministic` provider works without credentials. It processes every non-empty record in the exact requested vehicle/market scope. Original BMW feedback types (`Likes`, `Difficult to Use`, `Defect`, `Wants`) take precedence over text rules; category metadata and keywords map evidence to stable customer themes. Imported `study_aggregate`, `sales_aggregate`, `document_context` and `context` records remain context even when their wording or metadata mentions complaints. BMW survey-question prefixes are separated from the customer's response before keyword classification. Opposing signals within a theme are surfaced as potentially contrasting experiences. Positive-only themes generate preservation requirements.

The classification confidence is a rule heuristic, not a probability. Imported record counts are not population prevalence. Acceptance criteria carry explicit PM assumptions, including the proposed 80% participant-evaluation target. PMs must approve the actual evaluation protocol, participant sample and target before approving a requirement.

Scores use a documented 0–5 reference heuristic. Customer impact is `min(5, 1.5 + log2(1 + topic evidence count) / 3)`; market relevance is 4 for exact scoped evidence; strategy=3, differentiation=2, feasibility=3 are assumptions requiring PM input. Each proposal repeats this explanation. Unrelated new evidence does not affect a topic's factor values. Sorted IDs ensure identical input yields identical results regardless of order.

## OpenAI mode

Explicitly request `provider="openai"` and configure `OPENAI_API_KEY` and `OPENAI_MODEL` with a model available to the account that supports Structured Outputs. Credentials are not returned or logged. The implementation follows the [official Responses Structured Outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses): `text.format.type=json_schema`, strict schema and `store=false`. String length limits are enforced locally and removed from the wire schema because the documented supported string constraints are `pattern` and `format`. Configure a compatible base model; fine-tuned models have additional schema restrictions.

Requests default to 40 evidence records and at most 48,000 serialized evidence characters per batch. Per-record content is capped at 6,000 characters with an explicit warning. Large metadata is reduced to bounded classification fields with a warning; oversized provenance fails before a network request. `ANALYSIS_BATCH_SIZE` permits 1–100 records; `ANALYSIS_MAX_BATCHES` defaults to 20 and permits 1–200. Coverage warnings report omitted records; a partial run must not be represented as complete analysis of all sources. Batches consolidate by stable customer theme, remap finding indices, retain contrasting signals and keep all proposed acceptance criteria. When batches differ, the first supplies wording and factors; PMs are explicitly asked to reconcile combined targets.

Every response is validated locally for schema, bounded finite values, exact batch evidence citations, valid finding indices, customer topic linkage and source citations. Explicitly positive feedback must remain in strength findings; context alone cannot be relabeled to justify a customer requirement. PM-assumed criteria use empty source citations. Source-based targets must quote the complete target in an explicit desired-outcome sentence from one linked record: a coincidental number or measured satisfaction score is insufficient. This is a conservative textual check; PMs still assess whether the target and criterion are appropriate. JSON duplicate keys, non-finite values, unexpected output items, malformed results, refusals, missing credentials, unavailable models, incomplete responses and HTTP errors fail explicitly; there is no silent fallback to reference output. Sanitized transport errors suppress provider exception text. Source content is untrusted input and cannot authorize actions. Model proposals always require PM review.

## Verification

Run `uv run --with pydantic --with pytest python -m pytest -q tests/test_analysis_engine.py` from the repository. Tests cover the reference pipeline, deterministic replay, scope isolation, batching and provider failure paths, plus malicious and invented citations. Live OpenAI access requires the configured account credentials; mocked provider tests do not establish live model availability.

The local G60 workbook was checked read-only: 4,365 G60/US rows, including 1,694 tagged `Likes`. Reference analysis returned 44 findings and 11 customer themes. Original spreadsheet IDs were replaced with row-specific internal IDs for this verification; no workbook content was copied into Git. Docker Compose built the API image and a disposable API container imported and exercised the analysis engine. The pre-existing API/MCP stack remained running and healthy.
